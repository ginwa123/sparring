changeevidence

kabelweb bench sizing — the equal-spec trap

cgroup CPU quota is not pinning: getCpuCount() inside the container still reports the host's 16 CPUs, so the bench ran 4 accept loops plus a worker pool sized from 16 CPUs on a 2-CPU budget — the same class of bug as an unpinned GOMAXPROCS.

configpoint readlist (20)search (LIKE)
loop_count=4, pool = 16 (original)85.0 k53.0 k32.3 k
loop_count=2, worker_threads=285.0 k53.0 k32.3 k
loop_count=1, worker_threads=292.0 k75.2 k55.1 k
loop_count=1, worker_threads=3—72.3 k—

A second event loop busy-polls and steals half of the 2-CPU budget. One loop plus two workers is the right shape here.

Correctness

  • zig build test in ruangsql: 124/124 passing, leak-checked allocator.
  • scripts/smoke-db.sh ALL_PASS on all four frameworks (byte-identical JSON, same status codes).
  • Two bugs were caught by these gates during the work: pooled SELECT last_insert_rowid() returning 0, and a statement left un-reset holding an implicit read transaction that made BEGIN IMMEDIATE fail without honouring busy_timeout. A lock-holding-iterator variant deadlocked the suite and was reverted.
